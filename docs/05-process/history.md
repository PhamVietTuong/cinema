How to use it: add a new row at the top (newest first) whenever a feature is removed or a rule, default or seed value changes behaviour. Never edit an old row except to fix a wrong fact. Each row has the date, what was removed or changed, why, and the pull request or commit. "Owner decision" means the project owner asked for it; "reason not recorded" means neither the commit message nor the decision notes say why. The other docs do not describe anything listed here as live, apart from a one-line statement that something is not supported.

## Destructive upgrade blocks

Both blocks live in `cinemabe/sql/upgrade_db.sql`. Apply them to the local dev database only; any other environment needs the owner's fresh confirmation and a verified backup first. Run them with the API stopped (no payment in flight).

**Child ticket purge (2026-11-14).** The "Remove the child ticket category" block permanently deletes every invoice that has a ticket sold under the child patron category (exact `PatronCategory.Name` / ticket `PatronCategoryName`, matched by name or `PatronCategoryId`) together with its tickets, payments, food lines and `StockMovement` rows, then that category's `RoomTypePatronCategoryPrice` rows and the category itself, in one transaction. Redeemed points of purged Pending invoices go back to their users, and surviving invoices whose `ExchangedFromInvoiceId` pointed at a purged one get it set to NULL. It is one-shot, not merely idempotent: it records the database extended property `purge_child_ticket_done` in the same transaction and skips itself when that property exists, so a later category with the same name is never purged. Not reversed: points earned on purged Paid invoices, `PromotionProgram.UsedCount`, food stock.

**Gift card purge (2026-11-14).** The "Discount simplification" block permanently deletes every invoice that used a gift card (`Invoice.GiftCardAmount > 0`, or an `InvoicePayment` with `Method = 3`) together with its tickets, payments, food lines and `StockMovement` rows, in one transaction, and gives the redeemed points of purged Pending invoices back to their users. It then drops `Invoice.GiftCardId`/`GiftCardAmount`, the `GiftCard` table, `PromotionProgram.StacksWithMembershipDiscount` and `MemberShip.DiscountPercent`. Not reversed: loyalty points earned on purged Paid invoices, `PromotionProgram.UsedCount`, food stock, and historical revenue, which drops by the purged invoices.

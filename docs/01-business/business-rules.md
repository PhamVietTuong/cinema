## 1. Seat lock / booking concurrency

| Rule | Description | Enforced at |
|---|---|---|
| Advisory seat lock is process-local | `_lockedSeats` (`ConcurrentDictionary<string,(ConnectionId,LockedAt)>`, keyed `"{showTimeId}:{roomId}:{seatId}"`) and `_bookingGates` (`ConcurrentDictionary<string, SemaphoreSlim>`, keyed `"{showTimeId}:{roomId}"`) are static in-memory dictionaries in `BookingManager` — not distributed, lost on restart, not shared across instances. No `IDistributedCache`, Redis, or any distributed-lock class exists anywhere in the backend (verified by repo-wide search, zero hits) — confirmed still the case despite any branch/PR naming suggesting otherwise. | `BookingManager.cs:27,32` |
| Lock duration = 5 min, lazy expiry | `IsSeatLocked` compares `DateTime.UtcNow - info.LockedAt > TimeSpan.FromMinutes(5)`. Expiry is **lazy** — only evaluated when `IsSeatLocked` is called (i.e. on the next `GetSeatsAsync`/`ComposeInvoiceAsync`), not swept by a background timer. A stale entry can sit in `_lockedSeats` indefinitely until something reads it. | `BookingManager.IsSeatLocked` (`:1907`, TTL compare at `:1918`) |
| Pending-invoice hold = 15 min | `PendingBookingReaper._holdWindow` = 15 min, reaper runs every 1 min (`_interval`), calling `ExpireStalePendingBookingsAsync(15m)` which cancels every Pending invoice older than the cutoff, deactivates its tickets, and restores points/food stock. An invoice whose payment was started (`PaymentReference` set) gets an extra 15-minute grace (`_paymentGrace`, matching VNPay's `vnp_ExpireDate`) so a late IPN can still confirm it; the cost is that an abandoned in-flight payment holds its seats up to 30 minutes. A VNPay payment that is confirmed after the invoice was cancelled still gets `RspCode 02` with no ticket, so the window must not be shortened below the payment page's life. This is an independent, DB-backed timer — not the same mechanism as the 5-min advisory lock above; the two must not be conflated (a seat can show "unlocked" advisoraly while its invoice is still Pending and blocking rebooking, or vice versa). Frontend's `booking-checkout.component.ts` hardcodes a cosmetic `HOLD_SECONDS = 15*60` countdown mirroring this window — it enforces nothing; if the reaper's window ever changes, this constant must be updated to match or the UI desyncs from real expiry. | `PendingBookingReaper` |
| DB-level anti-double-booking | Unique filtered index on `InvoiceTicket(ShowTimeId,RoomId,SeatId) WHERE IsActive=1` — the only cross-instance guarantee against double-booking. If violated, a `SeatUnavailableException` is caught in both `CreateBookingAsync` and `SellAtCounterAsync` and rethrown as `InvalidOperationException("One or more selected seats were just booked by someone else.")`, after rolling back the transaction. | `create_db.sql`/`upgrade_db.sql`; `InvoiceTicket` config |
| In-process booking gate | `SemaphoreSlim(1,1)` per `(showTimeId,roomId)`, acquired before `ComposeInvoiceAsync` + invoice insert in both `CreateBookingAsync` and `SellAtCounterAsync`, released in `finally`. Serializes the "read booked seats → validate → insert" sequence within one process so two concurrent requests can't both pass the "seat free" check. Semaphores are created lazily via `GetOrAdd` and never removed/evicted — not currently a practical problem given the bounded showtime/room count, but worth knowing. | `BookingManager.BookingGate` |
| Double (paired) seats booked together | If any requested seat belongs to a `SeatGroupId`, every seat sharing that group must also be in the same request, else `InvalidOperationException("A double seat must be booked together with its partner.")`. The requirement is enforced at the booking-validation layer only — the advisory lock/hub methods still operate per individual seat id. | `BookingManager.cs:468-480` |
| Aisle cells | A `Seat` with `Kind=Aisle` is a non-bookable gap cell (always `IsActive` true, `SeatGroupId` null). `GetSeatsAsync` returns it as `IsAisle`, `Status=Available`, `Price=0` (`BookingManager.cs:72-86`); booking it is refused with `Seat {row}{col} is an aisle and cannot be booked.` (`BookingManager.cs:513`); `BlockSeatAsync` refuses it (`IncidentManager.cs:213`). The advisory `LockSeat` call has no aisle check (`BookingManager.cs:1885`), but a locked aisle still cannot be booked. Aisles are excluded from seat counts: bookable-seat counts, the schedule board, showtime capacity and staff-report occupancy all filter `Kind != Aisle` (`SeatStore.cs:15,58`, `ScheduleBoardStore.cs:30`, `ShowTimeStore.cs:44`, `StaffReportStore.cs:246`). `Room.TotalRows`/`TotalColumns` still describe the whole grid including aisles. Seat-map save (`RoomManager.cs:277-281`) forces an aisle to `SeatGroupId=null`, `IsActive=true`; aisles never count toward a double-seat pair (`RoomManager.cs:251-253`), and a seat with upcoming tickets cannot be turned into an aisle (`RoomManager.cs:257-270`). An aisle can never be priced: promotion-program prices with `SeatKind.Aisle` are rejected (`PromotionProgramManager.cs:191-193`). | `SeatKinds.cs`, `BookingManager`, `RoomManager` |
| Advisory lock is checked on every booking | A seat held by another connection is rejected with `InvalidOperationException("Seat {id} is being held by another user.")`. With a `ConnectionId` the booker's own held seats still pass; **without** one (a direct API call) any live lock blocks the booking, since it cannot be the caller's. The lock stays advisory: the DB unique index is the only cross-instance guarantee. | `ComposeInvoiceAsync` |
| Seat lock lifetime | A lock lasts 5 minutes from the first `LockSeat` (`_seatLockTtl`). Re-locking a seat the same connection already holds does **not** renew it; after expiry the same or another connection can take a new lock. `UnlockSeat` returns true only when it removed the caller's own lock, and `BookingHub` broadcasts `SeatUnlocked` only then. An expired lock is dropped lazily (no sweep), so other viewers' screens may keep showing the seat as held until they refresh. | `BookingManager.LockSeat`/`UnlockSeat`, `BookingHub` |

## 2. Booking → payment → ticket lifecycle

| Rule | Description | Enforced at |
|---|---|---|
| State machine | `Available` →(LockSeat hub)→ `Locked` (advisory/Reserved) →(5 min elapse, lazy)→ `Available`; `Locked`/`Available` →(CreateBooking/SellAtCounter succeeds)→ `Booked(Pending or Paid)`; `Booked(Pending)` →(ConfirmPayment/Callback success)→ `Booked(Paid)`; `Booked(Pending)` →(15-min reaper; customers cannot cancel)→ `Available`; `Booked(Paid)` →(ValidateTicket/gate scan)→ `Used` (seat stays Booked). Seat `Status` from `GetSeatsAsync` gives `Occupied` (Pending or Paid invoice) priority over `Reserved` (advisory lock), else `Available`. | `BookingManager`, `BookingHub` |
| Online booking starts Pending | `CreateBookingAsync` creates `Invoice{Status=Pending, Channel=Online}`; re-validates everything server-side (seats free, patron category, stock, points, promos) inside the `BookingGate` + a DB transaction; unlocks the booker's own advisory locks and broadcasts `SeatBooked` to the room. | `BookingManager.CreateBookingAsync` (`:136`) |
| Online booking checks | Online only (counter sales are exempt from all four), enforced in `ComposeInvoiceAsync` before pricing: (1) the showtime, its movie and its theater must be active and `now < StartTime + Booking:OnlineSalesCloseMinutesAfterStart` (default 0), else "This showtime is not open for sale."; (2) the seat count requested (before dedupe) may not exceed the theater's `Theater.MaxSeatsPerBooking` (default 10, 1-50, set in CinemaAdmin; a double seat is two physical seats and counts as two toward the cap); (3) a film with `MinAge >= 13` (fixed online threshold, independent of the gate's `Gate:AgePromptMinAge`) needs `CreateBookingRequest.AgeConfirmed=true` (CinemaUser shows the checkbox); (4) a `RequiresIdCheck` patron category is refused online (hidden in the selector) and sold only at the counter. | `BookingManager.ComposeInvoiceAsync`, `EnsureOnlineSaleOpen` |
| Counter sale is Paid at creation | `SellAtCounterAsync` creates the invoice already `Paid`, with tenders, in one transaction — it never passes through Pending. Reuses the same seat/pricing/stock/points validation as online booking via `ComposeInvoiceAsync`. | `BookingManager.SellAtCounterAsync` (`:230`) |
| Only Pending can be paid | `InitiatePaymentAsync`, `ConfirmPaymentAsync` both require `Status==Pending` and caller ownership (object-level check against the JWT `userId`); return `false`/`null` (not an exception) otherwise — no double confirm. Customers cannot cancel a Pending invoice; only the reaper below clears it. | `BookingManager` |
| Stale-Pending auto-expiry | `ExpireStalePendingBookingsAsync(15m)`, runs every 1 min via `PendingBookingReaper`, batch-applies the expiry side effects below to every Pending invoice older than the cutoff. This is the only path that cancels a Pending invoice. | `PendingBookingReaper` |
| Expiry side effects | Inside one DB transaction: `Status=Cancelled` → `CancelFoodOrder` (releases food-order state) → `DeactivateTicketsAsync` (frees seats) → `RestoreRedeemedPointsAsync` (gives back `PointsRedeemed`) → `RestoreFoodStockAsync` (restocks reserved inventory, batched for the sweep job). | `BookingManager.ExpireStalePendingBookingsAsync` |
| Paid side effects | `FinalizePaidInvoiceAsync`: (1) `Status=Paid`, `PaymentReference` set, `PaidAt=UtcNow`; (2) if `FinalAmount>0`, append `InvoicePayment{Method=Online, Amount=FinalAmount, Reference=paymentReference}`; (3) accrue loyalty points + re-evaluate membership tier + mark used `PromotionProgram.UsedCount+=1` if a program applied (code or auto-apply); (4) send a best-effort email/SMS e-ticket confirmation (template-rendered, falls back to a hardcoded string; a notification failure never fails the payment). | `BookingManager.FinalizePaidInvoiceAsync` |
| Gate age check | A ticket whose film `MinAge >= Gate:AgePromptMinAge` (default 13: T13, T16, T18) returns `AgeCheckRequired` and stays unused until the keeper re-scans with `AgeConfirmed`. Rating K (under 13 with a guardian) is admitted with `ScanTicketResultDTO.GuardianRequired=true` and the gate shows a banner. A ticket sold under a patron category that has `RequiresIdCheck` (found by the ticket's `PatronCategoryId`; a deleted category or a null id counts as false) carries `ScanTicketResultDTO.RequiresIdCheck=true` on every outcome that identifies a ticket, and the gate shows a "check the holder's ID" banner with the category name. The reminder never blocks admission, and an admitted result with it is not auto-cleared (same as the K banner). The flag is loaded in the same query as the ticket (no extra round trip). Tests: `GateManagerTests.Scan_IdCheck*`. | `GateManager.EvaluateScanAsync`/`Result`, `InvoiceStore.GetGateTicketByQrAsync` |
| Gate check-in | `CinemaController.Gate.Scan` (staff): requires a `Paid`, active ticket inside the time window and the staff member's theater, then admits through one atomic `UPDATE ... WHERE IsUsed = 0 AND IsActive = 1` that stamps `UsedAt`/`UsedByUserId`, and audits every attempt. `PaymentController.ValidateTicket` (Admin only) uses the same atomic admit and rejects deactivated tickets, but applies **no** theater or time-window check. | `GateManager`, `BookingManager.ValidateTicketAsync` |
| Refunds are not supported | There is no refund, partial refund or gateway-side refund call: `IPaymentGateway` has no refund method and no `Refunded` invoice status exists. A `Paid` invoice can only change status through the constrained admin `UpdateStatusAsync` (next row), which does not reverse points/stock or touch any gateway. `Cancelled` (restores points/stock) applies to `Pending` invoices. The enum ordinals `InvoiceStatus` 4 and `AuditAction` 4 are reserved (see the "Reserved ordinals, never reuse" row). | n/a (absence) |
| `InvoiceStatus.Failed` is dead code | Defined (value 3) but no code path currently sets it — a gateway/booking failure today just leaves the invoice `Pending` (real providers) or never creates one at all (thrown exceptions during `CreateBookingAsync`/`SellAtCounterAsync` roll back the whole transaction). | `InvoiceStatus` enum |
| Admin status override is constrained | `InvoiceAdminManager.UpdateStatusAsync` rejects undefined enum values (model binding accepts any integer) and only allows these moves: `Pending → Paid` (adds an `ADMIN-OVERRIDE` cash payment row, accrues loyalty, consumes the promo), `Pending → Cancelled/Failed` (frees the seats, closes the food order, restores redeemed points and food stock), `Paid → Cancelled/Failed` (frees the seats and closes the food order; points spend is **not** refunded — that is a manual business decision), and `Cancelled ↔ Failed`. Reopening (`→ Pending`, or `Cancelled/Failed → Paid`) is refused because the seats may already be rebooked. The move is an atomic conditional `UPDATE ... WHERE Status = <from>` inside a transaction. | `InvoiceAdminManager.UpdateStatusAsync` |

## 3. Payments — VNPay callback authority

| Rule | Description | Enforced at |
|---|---|---|
| **Callback-authoritative, not redirect-authoritative** | Every real gateway's `VerifyPaymentAsync` (the synchronous, browser-redirect-driven confirm path) is hardcoded to return `Success=false` with a message pointing at the callback — same pattern in `VnPayGateway`. Only `SandboxPaymentGateway.VerifyPaymentAsync` ever returns `Success=true` (dev/local convenience); that gateway is registered only in Development or when `Payments:EnableSandbox=true`. A callback or confirm is accepted only when the resolved gateway's name equals `Invoice.PaymentMethod` (set at `InitiatePayment`), so an unsigned Sandbox callback can never finalize a VNPay invoice. Only the signed server-to-server callback through `PaymentCallback` → `HandlePaymentCallbackAsync` can flip a real-provider invoice to `Paid`. The frontend's `payment-return` page polls `GetInvoice` for ~30s after redirect and shows "Payment pending" if the IPN hasn't landed — expected, not a bug, when the backend isn't reachable from the gateway's servers. | `VnPayGateway.VerifyPaymentAsync` |
| VNPay IPN response contract | The only acceptable response shape is exact JSON `{"RspCode": "..", "Message": ".."}`. Mapping: `Confirmed`→`00 Confirm Success`; `PaymentFailedAcknowledged`→`00 Confirm Success` (acknowledged even though payment failed, so VNPay stops retrying); `OrderNotFound`→`01 Order not found`; `AlreadyConfirmed`→`02 Order already confirmed`; `NotPending`→`02 Order already confirmed` (reused); `InvalidAmount`→`04 Invalid amount`; `InvalidSignature`→`97 Invalid signature`; anything else (`Rejected`/`Error`/unmapped)→`99 Unknown error`. Wrong shape/status causes VNPay to retry the IPN for up to 50 minutes (10 attempts, ~5 min apart). Any unhandled exception during a VNPay callback still returns HTTP 200 with `RspCode=99` so VNPay doesn't retry-storm on a transient server error; other providers fall through to `HandleException` (HTTP 500). | `VnPayGateway.BuildIpnResponse` |
| VNPay amount is ×100 | `vnp_Amount` = VND amount × 100 (VNPay quirk); `ParseCallback` divides by 100 before comparing to `invoice.FinalAmount`. VNPay signing itself is HMAC-SHA512 over the sorted, URL-encoded `vnp_*` query params (excluding `vnp_SecureHash`/`vnp_SecureHashType`) using `Payments:VnPay:HashSecret`. | `VnPayGateway` |
| Callback idempotency | `HandlePaymentCallbackAsync` checks `invoice.Status==Paid` first and returns `AlreadyConfirmed` without re-running `FinalizePaidInvoiceAsync` — no double loyalty accrual, no duplicate `InvoicePayment` row. Full outcome matrix: `InvalidSignature`/`InvalidOrderReference`/`InvalidAmount` from gateway parse → no invoice touched; success but invoice not found → `OrderNotFound`; success, invoice already `Paid` → `AlreadyConfirmed`; success, invoice status neither `Pending` nor `Paid` (e.g. `Cancelled`) → `NotPending`; `PaymentFailed` on a `Pending` invoice → `PaymentFailedAcknowledged` (invoice stays Pending so the customer can retry); `Paid` on a `Pending` invoice → `Confirmed`, runs `FinalizePaidInvoiceAsync`. | `BookingManager.HandlePaymentCallbackAsync` The Pending → Paid (and the reaper's Pending → Cancelled) change is an atomic conditional `UPDATE ... WHERE Status = Pending` (`InvoiceStore.TryTransitionStatusAsync`) inside a transaction, so two concurrent deliveries, or an IPN racing the expiry job, apply loyalty points and the payment row once; the loser gets `AlreadyConfirmed` (or `NotPending` if the invoice was cancelled). |
| Amount cross-check | `ReceivedAmount` (when the gateway reports one) is compared against `invoice.FinalAmount`, both rounded to whole VND via `(decimal)(long)Math.Round(...)` to match `VnPayGateway.CreatePaymentAsync`'s own `(long)Math.Round(amount)` rounding — a mismatch here rejects the callback as `InvalidAmount` and leaves the invoice untouched. No currency field travels through the callback model at all — the system is implicitly VND-only. | `BookingManager.HandlePaymentCallbackAsync` |
| `PaymentCallback` is `[AllowAnonymous]` | Called by the gateway's own servers, not the browser — all trust comes from the per-gateway signature check inside `ParseCallback` (VNPay: HMAC-SHA512 over sorted/encoded params), never from ASP.NET auth. | `PaymentController.PaymentCallback` |
| Zero-amount checkout skips gateway | A booking whose `FinalAmount<=0` finalizes `Paid` immediately with `PaymentReference="ZERO-AMOUNT"` and `Provider="None"` in the response DTO — no `IPaymentGateway` is ever invoked, so gateway-specific tests/monitoring won't see these transactions. | `BookingManager.InitiatePaymentAsync` |

## 4. Pricing formula

| Rule | Description | Enforced at |
|---|---|---|
| **Pricing formula** | `price = round(roomTypePrice(category, roomType) * priceFactor + threeDSurcharge + showTimeRoom.BasePrice, 2)`, computed once per `(ShowTime, Room)` pair and reused for every seat/category in that booking. `priceFactor`: Holiday wins outright (if the showtime's date matches any `Holiday.Date`, `priceFactor = holiday.PriceMultiplier` and the weekday/TimeSlot matrix below is not even queried); otherwise, find the theater `TimeSlot` whose `[StartTime,EndTime)` window contains the showtime's time-of-day and look up `TicketPrice` for `(TheaterId, RoomTypeId, TimeSlotId, DayOfWeek)` — match found → `priceFactor = TicketPrice.PriceMultiplier`, else `priceFactor = 1.0`. `threeDSurcharge` = `RoomType.ThreeDSurcharge` only if `ShowTime.ProjectionForm==ThreeD` (zero otherwise, lookup skipped for 2D). `showTimeRoom.BasePrice` is a manual flat amount set per showtime+room at create/update time, added last as a flat addend — never multiplied by `priceFactor`. | `BookingManager.BuildSeatPricingContextAsync` |
| Category has no fallback price | `RoomTypePatronCategoryPrice` is the only price read at booking time for a given `(RoomTypeId, PatronCategoryId)` — a category with no override row for that RoomType is not priced/offered at all, silently (no error, it just doesn't appear in `SeatPricingContext`). `PatronCategory.Price` is only the "before RoomType overrides" seed value documented on the entity; it is never read by this code path. Only categories that are `IsActive` **and** have an override row make it into `SeatPricingContext`. | `BookingManager.BuildSeatPricingContextAsync` |
| Seeded time-of-day factors; late-night guidance | A fresh `insert_db.sql` seeds the `TicketPrice` factor per time slot as `Sáng` 0.9, `Chiều` 1.0, `Tối` 1.2, `Khuya` (22:00-23:59) 0.85, each multiplied by a room-type factor (IMAX 1.5, 4DX 1.8, Deluxe 1.4, 3D 1.2). Late-night is discounted because Vietnamese chains sell after-22:00 shows below the evening rate. Existing databases keep whatever multipliers they have (`upgrade_db.sql` does not rewrite them). The CinemaAdmin ticket-price dialog warns, without blocking save, when a slot starting at 22:00 or later is priced above the preceding slot on any selected day; pricing resolution itself is unchanged. | `insert_db.sql`; `ticket-price.dialog.ts` |
| Holiday overrides weekday matrix, never stacks | If the showtime's date is a `Holiday`, the `TimeSlot`/`TicketPrice` lookup is skipped entirely, not applied on top of the holiday multiplier. | `BuildSeatPricingContextAsync` |
| 3D surcharge & per-showtime BasePrice are flat adds | Both are added after the `roomTypePrice * priceFactor` multiplication, so they are immune to holiday/weekday surge pricing — they never interact with/get multiplied by `priceFactor`. | same |
| Seat-kind gating (2 layers) | (1) **PatronCategory ↔ SeatType**: whether a logical category can book a seat kind at all, at the theater — enforced structurally; "no row for that (category, SeatKind) pair" means impossible, not a runtime check (e.g. no Student/Double row means Students cannot book double seats). (2) **RoomType ↔ PatronCategory** (`RoomTypePatronCategoryPrice`): whether a category can book in a room class at all, and at what price — zero rows for a category in a RoomType = not offered there, full stop, no fallback to the theater-wide `PatronCategory.Price`. `PatronCategoryManager` additionally validates `SeatTypeId` belongs to the same `TheaterId` and rejects a duplicate `(TheaterId, Name, SeatTypeId)` triple. | `PatronCategoryManager`, `BuildSeatPricingContextAsync` |
| ShowTime scheduling validation chain | In order: (1) `ValidateWindow` — end must be after start ("A showtime must end after it starts."); on Create only, start must be in the future ("A showtime cannot be scheduled in the past."), Update skips this. (2) Load movie runtime. (3) `ValidateAgainstRuntime` — showtime window must be at least as long as the film ("'{movie}' runs {N} minutes; the showtime must end no earlier than {time}."), skipped if `Duration<=0`. (4) `ValidateMovieAvailability` (future-gated) — movie must be `IsActive` ("no longer showing; reactivate the movie before scheduling it"), and the showtime's start **date** must fall within `[ReleaseDate, EndDate]` inclusive (`EndDate==null` = open-ended). (5) If a room is assigned: theater must be `IsActive` (checked first), room `Status` must be `Active` (explicit message for `Maintenance`, generic "not in service" otherwise); `ValidateRoomSupportsFormat` — a `ThreeD` showtime requires `RoomType.SupportsThreeD`, not future-gated, always enforced; `HasRoomOverlapAsync` rejects if the window overlaps any other showtime in that room, expanded by the RoomType's `TurnoverBufferMinutes` on each side (message distinguishes a true double-booking from a too-tight turnover gap). A showtime has exactly one room assignment in practice — `ShowTimeRooms` is a collection but every read path uses `.FirstOrDefault()`. | `ShowTimeManager` (`ValidateWindow`→`HasRoomOverlapAsync`) |

## 5. Promotions / loyalty

| Rule | Description | Enforced at |
|---|---|---|
| Single promotion mechanism, triggered one way | `PromotionProgram` is the only pricing entity. A program is triggered by exactly one of `Code` (customer-entered at checkout) **xor** `AutoApply=true`, enforced at save time — never both. Code path: `FindUsableProgramByCodeAsync` looks it up by `Code`, requires `IsPublished`, within `[StartDate,EndDate]`, under `MaxUsage` (when set), and in scope (`MatchesProgramScope`); throws `InvalidOperationException` on an unusable code. Auto-apply path: `FindBestAutoApplyProgramAsync` filters candidates by `MaxUsage`/`UsedCount` (a program at its cap is skipped), the program's `MovieId` (a movie-scoped program only discounts that movie), `AllowedChannelsMask`, `ExcludeHolidays`, schedule match (theater/day-of-week/time window via `PromotionProgramSchedule`), and `Eligibility` (Members requires the user's tier `MinPoints` to meet-or-exceed the program's threshold); best candidate = highest total saving across the top `N = MaxTicketsPerTransaction ?? all` units (most valuable tickets discounted first), ties broken by lowest `DisplayOrder` then lowest `Id`. Either way, the saving is computed per-ticket-unit via `ComputeProgramSaving` (not on the whole order total; a food-only sale cannot get a saving from a code/auto-apply program). The winning program's `Id` is recorded on the invoice's `PromotionProgramId`. `MaxUsage` is checked at booking time but `UsedCount` is only incremented when the invoice turns `Paid` (an atomic `UPDATE ... SET UsedCount = UsedCount + 1`, `PromotionProgramStore.IncrementUsedCountAsync`), so several Pending invoices can pass the check at `UsedCount = MaxUsage - 1` and the cap can be exceeded by the number of in-flight bookings — a known, accepted limit. | `BookingManager.ComputePricingAsync` |
| `AutoApply` restrictions | Only `Everyone`/`Members` eligibility can auto-apply — `StudentOrTeacher`/`AgeLimit` have no online verification and are rejected from `AutoApply` at save time. `Info` mechanic (display-only) is also rejected from `AutoApply`. `AutoApply` and `Code` are mutually exclusive by design — a program either auto-applies invisibly or is triggered by a customer-entered code, never both; this is the only rejection rule for the pairing. | `PromotionProgramManager.ValidateAsync` |
| Per-theater cap on the promotion saving | The promotion saving (code or auto-apply) may not exceed a percent of the **summed ticket list prices**: `Theater.MaxPromotionDiscountPercent` (0-50, default 50) normally, or `Theater.MaxHolidayPromotionDiscountPercent` (0-100, default 50) when a `Holiday` row exists on the showtime date (same lookup as `ExcludeHolidays`). Applied after `ComputeProgramSaving` (and its `MaxDiscountAmount`) in three places so they always agree: the real price (code path and auto-apply), the choice of the best auto-apply program (programs are compared on their capped saving, ties by `DisplayOrder` then `Id`), and the discount-code preview (`ValidateDiscountCodeAsync`). The preview also reports `Capped` (true only when the cap actually reduced the saving), `UncappedAmount` (the saving before the cap; `DiscountAmount` stays the capped value) and `CapPercent` (the theater's real cap, 0 when not capped); CinemaUser shows "the theater limits this promotion to X%" in the discount dialog and under the applied code at checkout. The booking price is unchanged. When the theater cannot be resolved the cap falls back to 50% (`CreateBookingAsync_TheaterCannotBeResolved_FallsBackToTheFiftyPercentCap`). Online and counter sales share the path. A food-only sale has no ticket units, so the saving is 0 and no theater lookup happens. Points redemption and points earning are **not** capped (points still cover up to 100% of the remainder). Saved through `TheaterManager` (range 400 otherwise); on update an omitted (null) cap keeps the stored value, and only a set value is range-checked; a code whose capped saving is 0 is treated as not applied (no invoice link, no usage count). Tests: `BookingServiceTests.CreateBookingAsync_ProgramOverTheCap_*`, `_HolidayShowtime_UsesTheHolidayCap`, `ValidateDiscountCodeAsync_OverTheCap_*`, `TheaterManagerTests`. | `BookingManager.GetPromotionCapPercentAsync`/`CapPromotionSaving`, `TheaterManager.ValidatePromotionCaps` |
| One program per invoice, no tier percentage | Pricing order is: list price, then at most one `PromotionProgram` (code or auto-apply, saving capped per theater, see above), then loyalty-points redemption (up to 100% of the remainder), then the gateway. There is no membership-tier percentage discount and no gift cards; a tier's `Name`/`MinPoints`/`MaxPoints` only define points ranges, still gate programs through `MinMemberShipId` and points still accrue. `MaxDiscountAmount` caps the *summed* per-unit saving, post-`ComputeProgramSaving`. Tests: `BookingServiceTests.TierMemberWithoutProgram_PaysListPrice_NoTierPercentage`, `TierMemberWithProgram_PaysProgramPriceAlone`. | `BookingManager.ComputePricingAsync` |
| Loyalty points earned | `pointsEarned = (int)(invoice.FinalAmount / pointsPerUnit)` — integer division, truncates, no partial points; runs only when an invoice transitions to Paid and only for invoices with a `UserId` (counter sales with no customer account earn nothing). `FinalAmount` here is **after** all discounts/promotions/points-redemption deductions — points are earned on what was actually paid. Membership tier is then re-evaluated to the **highest** tier whose `MinPoints` the new balance qualifies for — upgrades happen immediately; no explicit downgrade logic exists. | `BookingManager.ApplyPaidSideEffectsAsync` |
| Loyalty points redeemed | At booking time: `maxByBalance = user.Points`, `maxByAmount = (int)(finalAmountSoFar / pointValueVnd)`, `pointsRedeemed = min(requestedPointsToRedeem, maxByBalance, maxByAmount)`; `pointsValue = pointsRedeemed * pointValueVnd`; deducted from `finalAmount` and added to `discountAmount`; the points are spent immediately (reserved at booking time, not deferred to payment success) through one atomic conditional `UPDATE ... SET Points = Points - n WHERE Points >= n` (`UserStore.TryDeductPointsAsync`), so two concurrent bookings cannot spend the same points — the loser throws `"Not enough loyalty points."` and its transaction rolls back — and restored if the booking is cancelled/expires. Redemption happens after promotion pricing has produced `finalAmount` and may cover up to 100% of it. A `DryRun` booking computes but does not persist the deduction. | `BookingManager` (booking-time) |
| Points/value rates are independent | `PointsPerUnit` (VND spent per point earned) and `PointValueVnd` (VND value of 1 point redeemed) are two independently configured rates, not required to be equal/inverse. Rates are **per theater only — there is no global setting**. Resolution: the theater's own `LoyaltySetting` row → built-in defaults (`DefaultPointsPerUnit=1000`, `DefaultPointValueVnd=10`), i.e. **1,000 VND spent = 1 point; 100 points = 1,000 VND (1 point = 10 VND)**. An admin edits a theater's rate on its *Loyalty Points* tab (inputs show `.` thousands separators, e.g. `1.000`) or resets it to the default (deletes the row). `SaveAsync` requires a `TheaterId` that exists and both rates `>0`. The user site shows the theater's rate at checkout. | `LoyaltySetting`/`LoyaltyRates` |

## 6. Auth / account rules

| Rule | Description | Enforced at |
|---|---|---|
| Account lockout | `_maxFailedLogins=5`, `_lockoutDuration=15 minutes`. On the 5th consecutive failure, `LockoutEndUtc = now+15min` and the counter resets to 0 (the lockout window, not the counter, now governs). Any successful login clears both `FailedLoginCount` and `LockoutEndUtc`. During active lockout: 401 `"Account locked due to too many failed attempts. Try again in {n} minute(s)."` (`n` = ceiling of minutes remaining). Wrong 2FA codes count toward the same 5-failure limit (only while a code is pending); the 5th wrong code starts the lockout and burns the pending code, and `VerifyTwoFactor` refuses even a correct code during lockout. | `AuthManager.LoginAsync`, `VerifyTwoFactorAsync` |
| Only Active accounts sign in | `User.Status` must be `Active` for every sign-in path (password, 2FA verify, Google, Facebook); `Inactive` (soft-deleted by `DeleteUser`) and `Banned` get 401 `"This account is disabled."`. Tokens already issued stay valid until their 24h expiry (there is no revocation list), so a deactivated user's old JWT keeps working until then. | `AuthManager.EnsureAccountActive` |
| Last active Admin is protected | `UpdateUser` (demote, or set status other than Active) and `DeleteUser` throw `InvalidOperationException` ("Cannot remove, demote or deactivate the last active administrator.") when the target is the only remaining active Admin. | `AuthManager.EnsureAnotherActiveAdminRemainsAsync` |
| Password hashing | PBKDF2-SHA256, 100k iterations, 32-byte key, 16-byte salt, compared via `FixedTimeEquals`. Also transparently verifies legacy single-round HMAC-SHA512 hashes (`IsLegacy` = salt length ≠ 16 bytes) and silently rehashes to PBKDF2 on successful legacy-hash login (no user-visible effect). Wrong password → 401 `"Invalid credentials."` and increments the failure counter. | `AuthManager`/`PasswordHasher` |
| Email confirmation gates password login only | Checked **after** password verification (step 4 of login, after step 3's hash check) — so a wrong password on an unconfirmed account still reports `"Invalid credentials."`, not confirmation status (no enumeration via error message). Unconfirmed + correct password → 401 `"Please verify your email address before signing in."`. Registration (`RegisterAsync`) sets `EmailConfirmed=false` but still returns a full `AuthResponse` with a usable JWT immediately — the user is logged in even though unconfirmed; only subsequent **password** logins are blocked until confirmed. The JWT issued at registration keeps working until it expires regardless of confirmation state (no server-side revocation). | `AuthManager.LoginAsync`/`RegisterAsync` |
| Social login bypasses 2FA | Google and Facebook logins **always** call `BuildAuthResponse` directly — `TwoFactorEnabled` is never checked for either provider (code comment: "Google logins bypass the app's own 2FA (Google enforces its own)."). | `AuthManager` |
| Account linking by email | Google/Facebook lookup by email: no match → auto-create a `Customer` user (random unguessable password — password login impossible, placeholder phone `"g"`/`"f"` + 15 hex chars since phone is unique+required and the provider gives none, `EmailConfirmed=true` immediately); match found but not yet confirmed → signing in via the social provider proves email ownership, so the existing account is auto-confirmed; match found and already confirmed → logs into the existing account as-is, whatever role it currently has (not forced to Customer). Google requires `EmailVerified==true` on the provider payload (else 401 `"Google account email is not verified."`); Facebook can't distinguish "bad token" from "no email permission" so both collapse to the same 401 `"Invalid Facebook token."`. | `AuthManager` |
| 2FA code | A password login with `TwoFactorEnabled=true` short-circuits: generates a 6-digit numeric code (`RandomNumberGenerator`), SHA-256-hashes it (`TwoFactorCodeHash`), 5-minute expiry, emails it and also SMS's it if the user has a phone number; returns `AuthResponse{RequiresTwoFactor=true}` with no token. `VerifyTwoFactor` requires the code to regex `^\d{6}$`; wrong/reused/expired/not-enabled all collapse to the same 401 `"Invalid or expired code."` (no information leak about which cause applied) — on success the code is consumed (single-use). | `AuthManager` |
| JWT has no refresh/revocation | HMAC-SHA256, claims: `sub`=user id, `email`, `ClaimTypes.Name`, `ClaimTypes.Role` (the one and only role claim, one role per user), `jti` (new Guid per token, purely informational — no replay/blacklist tracking), and a conditional `theaterId` claim present only for `TheaterStaff` accounts. Fixed expiry (`JWT:ExpiryHours`, default 24h if unset) from issue time; no refresh-token mechanism — the client must log in again after expiry. Server refuses to boot if `JWT:Secret` is missing or the insecure built-in default. | `JwtTokenService` |
| 403 vs 401 convention | A role/scope mismatch on an authenticated token is **403 Forbidden**, never 401 — 401 is reserved for "not authenticated at all," because the frontend's `errorInterceptor` force-logs-out (dispatches `logout()`, navigates to `/auth/login`) on any 401 response, regardless of which endpoint triggered it. `TryGetBackOfficeScope`/`TryGetStaffScope` helpers follow this convention: Admin → unrestricted; theater-scoped role → pinned to its theater claim, fails (403, not 401) if the claim is missing or the role doesn't qualify at all. | `ApiControllerBase.HandleException`, `ClaimsPrincipalExtensions` | Exception: the frontend `errorInterceptor` does NOT log out on a 401 from the credential-check Identity calls (`Login`, `Register`, `GoogleLogin`, `FacebookLogin`, `VerifyTwoFactor`, `ForgotPassword`, `ResetPassword`, `ConfirmEmail`, `ResendVerification`, `ChangePassword`) - a wrong password there must show an inline error, not sign the user out.

## 7. Append-only enums / schema invariants

| Rule | Description | Enforced at |
|---|---|---|
| Enums are append-only, never renumber | `AuditAction`, `FoodOrderStatus`, `IncidentCategory/Severity/Status`, `InvoiceStatus`, `PaymentTender`, `SalesChannel`, `SalesGroupBy`, `ScanOutcome`, `StockMovementType/ReasonCode` are all persisted as `int` in the DB; several carry explicit "never renumber"/"do not reuse" comments in the source enum definitions. Only add new values at the end. | entity/enum definitions |
| Reserved ordinals, never reuse | `InvoiceStatus` value 4, `AuditAction` values 4 and 16, and `PaymentTender` value 3 are reserved gaps: no enum member uses them, and the enum source comments say "do not reuse". | Single shared `AuditLog` table | One insert-only table with no FKs (`TheaterId`, `ActorUserId`, `ApproverUserId`, `EntityId` etc. are plain Guid columns) specifically so the trail survives deletion of the entity/user/theater it references; discriminated by the `AuditAction` enum. `AuditAction.GateScan` (17) logs every scan outcome, not just admits, and is documented as "best-effort, not transactional." `ConsentChanged` (18) and `AgeConfirmed` (19) are the consent/age-attestation evidence rows (see "Promotional-email consent record" and "Age attestation record" below); like all audit rows they are staged on the unit of work and persisted by the caller's own save/transaction.
